## <a id="mem_20251120_001"></a>记忆1：DeepSeek-OCR 环境部署完成

**类型**: 中期记忆  
**分类**: 架构类  
**标签**: `deployment`, `vllm`, `cuda`, `dependency-conflict`, `environment`

### 摘要
Python 3.12 + CUDA 11.8 + vLLM 0.8.5 环境，解决依赖冲突

### 详细内容

#### 环境隔离
- 使用 UV 创建 `.venv-vllm`（Python 3.12），独立于其他项目环境
- 激活方式：`source .venv-vllm/bin/activate`

#### 核心依赖
- **PyTorch**：
  - `torch==2.6.0+cu118`
  - `torchvision==0.21.0+cu118`
  - `torchaudio==2.6.0+cu118`
  - 来源：`https://download.pytorch.org/whl/cu118`
- **vLLM**：本地 wheel `vllm-0.8.5+cu118-cp38-abi3-manylinux1_x86_64.whl`
- **flash-attn**：预编译 wheel `flash_attn-2.7.3+cu11torch2.6cxx11abiFALSE-cp312-cp312-linux_x86_64.whl`

#### 关键决策
1. **不使用 requirements.txt 的旧版本**
   - `transformers==4.46.3` / `tokenizers==0.20.3` 与 vLLM 0.8.5 冲突
   - vLLM 要求 `transformers>=4.51.1` / `tokenizers>=0.21.1`
   - 解决方案：在 `.venv-vllm` 中安装 vLLM 兼容版本

2. **避免源码构建 flash-attn**
   - 原因：源码构建时出现 "Invalid cross-device link" 错误
   - 解决方案：直接使用官方预编译 wheel（匹配 Python 3.12 + CUDA 11.8 + Torch 2.6.0）

3. **模型权重预下载**
   - 路径：本地 `models/deepseek-ocr/`
   - 避免推理时在线拉取导致卡死或超时
   - 下载方法：通过 HuggingFace 镜像（`HF_ENDPOINT=https://hf-mirror.com`）+ `hf download --max-workers 4` 完整下载 `deepseek-ai/DeepSeek-OCR`

#### 模型获取
```bash
export HF_ENDPOINT=https://hf-mirror.com
hf download deepseek-ai/DeepSeek-OCR \
  --local-dir models/deepseek-ocr \
  --max-workers 4
```

#### GPU 配置
- 服务器有 4 张 A100-PCIE-40GB（编号 0-3）
- GPU 0/1 通常被他人占用
- 使用 GPU 2 或 3：`CUDA_VISIBLE_DEVICES=2` 或 `CUDA_VISIBLE_DEVICES=3`

#### 相关命令
```bash
# 创建虚拟环境
python3.12 -m uv venv .venv-vllm

# 安装依赖
source .venv-vllm/bin/activate
uv pip install torch==2.6.0+cu118 torchvision==0.21.0+cu118 torchaudio==2.6.0+cu118 \
  --index-url https://download.pytorch.org/whl/cu118
uv pip install vllm-0.8.5+cu118-cp38-abi3-manylinux1_x86_64.whl
uv pip install flash_attn-2.7.3+cu11torch2.6cxx11abiFALSE-cp312-cp312-linux_x86_64.whl
uv pip install PyMuPDF img2pdf einops easydict addict Pillow numpy
```

## <a id="mem_20251120_002"></a>记忆2：课题组论文批量转换流程固化

**类型**: 中期记忆  
**分类**: 流程类  
**标签**: `workflow`, `pdf-to-markdown`, `batch-processing`

### 摘要
四步流水线：配置 → 推理 → 拆章 → 清理

### 详细内容

#### 标准流程
```bash
# 在 课题组大论文提取/ 目录执行
cd /home/xxy/projects/DeepSeek-OCR/课题组大论文提取

# 步骤1：修改 config.py 路径
python edit_config.py <论文文件名>.pdf

# 步骤2：大模型 PDF 推理（A100-40G，约10-30分钟）
cd /home/xxy/projects/DeepSeek-OCR
CUDA_VISIBLE_DEVICES=2 .venv-vllm/bin/python DeepSeek-OCR-master/DeepSeek-OCR-vllm/run_dpsk_ocr_pdf.py

# 步骤3：拆分章节
cd /home/xxy/projects/DeepSeek-OCR/课题组大论文提取
python split_chapters.py outputs/<论文名>/<论文名>.mmd outputs/<论文名>/chapters

# 步骤4：后处理清理
python postprocess_chapter_md.py outputs/<论文名>/chapters
```

#### 目录约定
- **工作目录**：`课题组大论文提取/`（所有论文相关工作在此目录下）
- **输入**：`课题组大论文提取/papers/` 存放待转换的 PDF 文件
- **输出**：`课题组大论文提取/outputs/<论文名>/` 存放所有输出
  - `<论文名>.mmd`：完整 Markdown 输出
  - `<论文名>_det.mmd`：检测信息（带边界框坐标）
  - `<论文名>_layouts.pdf`：布局可视化 PDF
  - `images/`：提取的图片（JPG 格式）
  - `chapters/`：拆分后的章节 Markdown 文件

#### 配置文件约定
在 `DeepSeek-OCR-master/DeepSeek-OCR-vllm/config.py` 中：
- `INPUT_PATH = '课题组大论文提取/papers/xxx.pdf'`（相对路径）
- `OUTPUT_PATH = '课题组大论文提取/outputs/xxx'`（相对路径，不含 `.pdf` 后缀）
- `MODEL_PATH = 'models/deepseek-ocr'`（本地路径）

#### 执行日志
所有论文的转换命令记录在 `课题组大论文提取/执行记录.md` 中，便于追溯和复现

## <a id="mem_20251120_004"></a>记忆4：章节拆分脚本 split_chapters.py

**类型**: 中期记忆  
**分类**: 工具类  
**标签**: `chapter-splitting`, `regex`, `markdown-processing`, `script`

### 摘要
智能识别章节标题，过滤无关内容，支持多种编号格式

### 详细内容

#### 核心功能
1. **章节识别**
   - 识别 `##` 级别标题作为章节分界
   - 排除子章节（如 `## 2.3`、`## 1.1.1`）

2. **内容过滤**
   - **保留**：摘要（中/英文）、正文章节、总结/展望
   - **过滤**：致谢、独创性声明、版权授权、目录/目次/图目录/表目录、参考文献、作者简历

3. **摘要合并**
   - 自动将"摘要"和"Abstract"合并为单一文件 `0-中英文摘要.md`

#### 章节编号支持
- `第X章 标题`（如 "第1章 绪论"）
- `X 标题`（有空格，如 "1 绪论"）
- `X标题`（无空格，如 "3开放海域鱼类统计"）

#### 特殊处理
- **目录页码行识别**：忽略目录中的页码行（如 "1 绪论. 1"）
- **子章节排除**：排除 `## X.Y` 形式（如 "2.3 多尺度回归"）
- **文件名标准化**：
  - 摘要 → `0-中英文摘要.md`
  - 正文章节 → `1-绪论.md`、`2-相关工作.md`、`3-基于深度学习的水下目标检测模型.md`

#### 用法
```bash
cd /home/xxy/projects/DeepSeek-OCR/课题组大论文提取
python split_chapters.py outputs/<论文名>/<论文名>.mmd outputs/<论文名>/chapters
```

#### 文件信息
- 路径：`课题组大论文提取/split_chapters.py`

## <a id="mem_20251120_005"></a>记忆5：Markdown 后处理脚本 postprocess_chapter_md.py

**类型**: 中期记忆  
**分类**: 工具类  
**标签**: `markdown-cleanup`, `html-to-markdown`, `heading-fix`, `script`

### 摘要
清理章节文件：移除页分隔符、转表格、修正标题级别、标准化图片路径

### 详细内容

#### 清理功能

1. **移除页面分隔符**
   - 移除 `<--- Page Split --->` 标记
   - 保持内容连续性

2. **HTML 表格转 Markdown**
   - 解析 `<table>` / `<tr>` / `<td>` / `<th>` 标签
   - 转换为标准 Markdown 表格格式
   - 保留 `<br>` 标签用于单元格内换行

3. **修正标题级别**
   - `## 1` / `## 第1章` → 保持 `##`（一级章节）
   - `## 1.1` → `### 1.1`（二级章节）
   - `## 1.1.1` → `#### 1.1.1`（三级章节）
   - 自动在编号与标题间补空格（如 `### 1.1标题` → `### 1.1 标题`）

4. **图片路径标准化**
   - `![](images/xxx.jpg)` → `![](../images/xxx.jpg)`
   - 因为章节文件在 `chapters/` 子目录，需要相对路径向上一级

5. **移除参考文献章节**
   - 移除 `## 参考文献` / `## References` 及其后续内容
   - 保持章节内容干净

#### 用法
```bash
cd /home/xxy/projects/DeepSeek-OCR/课题组大论文提取

# 处理单个文件
python postprocess_chapter_md.py outputs/<论文名>/chapters/1-绪论.md

# 处理整个目录
python postprocess_chapter_md.py outputs/<论文名>/chapters
```

#### 文件信息
- 路径：`课题组大论文提取/postprocess_chapter_md.py`
- 大小：5.1K
- 语言：Python
- 依赖：`beautifulsoup4`（用于 HTML 解析）

## <a id="mem_20251120_007"></a>记忆7：记忆系统执行方式：AI 智能交互 vs 僵化脚本

**类型**: 中期记忆  
**分类**: 方法论类  
**标签**: `memory-protocol`, `ai-interaction`, `methodology`, `clarification`

### 摘要
记忆协议应由 AI 直接执行，而非依赖脚本自动化

### 详细内容

#### 核心理念
记忆系统的价值在于 **AI 的智能判断和交互式确认**，而不是僵化的脚本自动化。

#### AI 职责
1. **分析实际变更**
   - 分析 Git 提交历史和文件变更
   - 智能推断完成的工作内容
   - 识别正在进行的工作

2. **智能判断重要性**
   - 应用协议 §5.1/5.2 标准
   - 过滤琐碎修改（格式调整、注释补充、拼写错误）
   - 识别有价值的记忆（架构决策、非显而易见的 Bug、环境差异、性能优化）

3. **交互式确认**
   - 展示推断结果给用户
   - 请用户补充细节、修正推断
   - 根据用户反馈调整记忆内容

4. **生成结构化记忆**
   - 手动生成记忆文件（Markdown + JSON）
   - 管理记忆索引和学习状态
   - 提交并推送到 memory 分支

#### 为什么不用脚本自动化

| 判断场景 | 脚本能力 | AI 能力 |
|---------|---------|---------|
| 区分"非显而易见的 Bug"与"拼写错误" | ❌ 无法判断 | ✅ 理解语义 |
| 区分"架构决策"与"临时调试" | ❌ 无法判断 | ✅ 理解上下文 |
| 与用户交互确认推断、补充细节 | ❌ 无法交互 | ✅ 自然对话 |
| 权衡记忆取舍、综合考量 | ❌ 无法权衡 | ✅ 智能决策 |

#### 协议中脚本的定位
协议中提到的 `memory_manager.py` 应理解为：
- **工具辅助**：自动生成文件结构、解析 Git 日志、格式化输出
- **不是决策者**：不替代 AI 的智能判断和交互确认

#### 实践经验
- 在本项目中，AI 亲自分析工作变更、与用户交互确认、手动生成 8 条结构化记忆
- 这种方式比自动化脚本更灵活、更准确、更符合实际需求

## <a id="mem_20251120_008"></a>记忆8：memory 分支为主工作分支，main 仅用于上游更新

**类型**: 中期记忆  
**分类**: 配置类  
**标签**: `git-workflow`, `branch-strategy`, `memory-primary-branch`

### 摘要
日常工作在 memory 分支，main 只作上游代码临时中转

### 详细内容

#### 分支设计

**memory 分支**（主工作分支）：
- **包含内容**：
  - `.memory/` 记忆系统目录
  - `课题组大论文提取/` 工作目录：
    - `papers/` 待转换论文
    - `outputs/` 转换结果（不提交，太大）
    - `split_chapters.py` / `postprocess_chapter_md.py` / `edit_config.py` 工具脚本
    - `转换论文使用说明.md` / `执行记录.md` 文档
  - `DeepSeek-OCR-master/` 源码（只调用，不修改）
  - `.venv-vllm/` 虚拟环境（不提交）
  - `models/` 模型权重（不提交，太大）
- **作用**：存放所有实际工作成果
- **推送目标**：`git@github.com:x0chaoren0s/DeepSeek-OCR.git` 的 `memory` 分支

**main 分支**（临时中转分支）：
- **包含内容**：DeepSeek-OCR 上游代码（纯净状态）
- **作用**：仅用于从上游接收代码更新
- **跟踪目标**：`https://github.com/deepseek-ai/DeepSeek-OCR.git` 的 `main` 分支

#### 日常操作

**平常工作**（99% 时间）：
```bash
# 始终保持在 memory 分支
git switch memory

# 所有工作在 memory 分支进行
# - 编写脚本
# - 转换论文
# - 执行 HARVEST/SYNC
```

**上游更新**（罕见场景）：
```bash
# 1. 切换到 main 分支
git switch main

# 2. 拉取上游更新
git fetch origin
git pull origin main

# 3. 如需将更新合并到 memory
git switch memory
git merge main --allow-unrelated-histories

# 4. 如果 config.py 被还原，重新配置
python edit_config.py <当前论文>.pdf
```

#### 设计原因

1. **DeepSeek-OCR 只是调用的工具**
   - 不需要修改源码
   - 只调用 `run_dpsk_ocr_pdf.py` 进行推理

2. **config.py 是临时配置文件**
   - 被上游覆盖无所谓
   - 有 `edit_config.py` 可以快速重新配置

3. **避免污染上游代码**
   - 所有实际工作成果（脚本、论文、输出、记忆）都在 `memory` 分支
   - 保持 `main` 干净，便于接收上游更新

#### Git 远程配置
```bash
# origin：上游只读
git remote add origin https://github.com/deepseek-ai/DeepSeek-OCR.git

# memory：用户 fork 可推送
git remote add memory git@github.com:x0chaoren0s/DeepSeek-OCR.git

# 查看远程配置
git remote -v
```
